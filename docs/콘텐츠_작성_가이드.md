# 콘텐츠 작성 가이드

- 작성일: 2026-11-10
- 누가 쓰나: 사람이 직접 쓸 때, 그리고 **LLM 프롬프트의 기준**으로 그대로 넣는다.
- 칸 구조는 `docs/data-model.md`, 검사는 `pipeline/validate.py`.

## 1. 칸별 쓰는 법

| 칸 | 규칙 | 좋은 예 | 나쁜 예 |
|---|---|---|---|
| `definition` | **무엇인지 + 왜 쓰는지**, 두 문장 안. 다른 전문용어를 쓰면 그 용어도 카드가 있어야 함 | "어떤 일이 끝나면 상대가 먼저 알려 주도록 주소를 등록해 두는 방식. 계속 물어보지 않아도 돼서 빠르다." | "HTTP 콜백 기반 이벤트 드리븐 통지 메커니즘." (전문용어로 전문용어를 설명) |
| `analogy` | 일상에서 누구나 겪는 장면 한 문장 | "택배 기사님이 도착하면 초인종을 눌러 주는 것." | 다른 기술로 비유하기 |
| `examples` | 업무 존댓말, **60자 안팎**, 상황마다 1개. 용어가 문장 안에 그대로 들어간다 | 아래 3장 참고 | 용어 없이 돌려 말하기 |
| `pitfall` | 현업에서 실제로 틀리거나 사고 나는 지점. "~하면 ~된다" 형태 | "같은 알림이 두 번 올 수 있다. 확인하지 않으면 결제가 두 번 처리된다." | "주의해야 한다." (무엇을?) |
| `interview_q` | 실제 면접관이 물을 법한 질문. "차이", "왜", "어떻게 확인" 형태가 좋다 | "OAuth를 쓰면 왜 비밀번호를 보관하지 않아도 되나요?" | "OAuth란?" (외운 답만 나옴) |
| `interview_a` | `interview_q`의 모범 답변. **소리 내어 30초**(3문장 안팎). 순서: 정의 → 이유·차이 → 경험이나 주의점. 면접 말투("~입니다") | "폴링은 우리가 계속 묻는 방식이고, 웹훅은 상대가 먼저 알려 주는 방식입니다. …" | 교과서 문단을 그대로 옮기기, 1분이 넘는 길이 |
| `expansion` | 약어일 때만. 원래 영어 이름 | API → Application Programming Interface | 약어가 아닌 용어에 쓰기 |
| `aliases` | 검색용. **띄어쓰기 변형, 다른 한국어 이름, 흔한 오타**를 넣는다 | 웹 훅, 웹후크, 콜백 URL | 뜻이 다른 용어 |

## 2. 발음 (`pronunciation`)

- 기준은 **현업에서 실제로 말하는 발음**이다. 외래어 표기법과 다르면 현업 발음을 따른다.
- `read_as`
  - `letters`: 한 글자씩 → API [에이피아이], SQL [에스큐엘]
  - `word`: 단어처럼 → SaaS [사스], OAuth [오-어스]
  - `mixed`: 섞어서 → OAuth2 [오어스 투], i18n [아이 에이틴 엔]
- 발음이 두 가지 이상 널리 쓰이면 `variants`에 넣고 `note`에 "둘 다 쓴다"고 적는다. 이것 자체가 현업 팁이다.
- `tts`는 영어 음성이 틀리게 읽을 때만 쓴다. 예: OAuth → `oh auth`

## 3. 예문 상황 3가지

| `context` | 장면 | 말투 | 예 |
|---|---|---|---|
| `meeting` | 고객사·팀 회의에서 제안하거나 설명 | "~하면 ~됩니다" | "결제 완료는 웹훅으로 받으면 주문 상태가 거의 실시간으로 바뀝니다." |
| `interview` | 면접에서 내 경험을 말함 | "~해서 ~했습니다" (1인칭 경험) | "폴링 요청이 너무 많아 웹훅으로 바꿔 서버 부하를 줄였습니다." |
| `review` | 문서·코드 리뷰 코멘트 | "~가 빠져 있어요. ~해 주세요" | "웹훅 중복 알림 처리가 빠져 있어요. 확인 코드를 추가해 주세요." |

- 셋 중 **2개 이상**. 용어 성격상 어색한 상황은 빼도 된다(예: 디자인 토큰의 면접 예문이 억지스러우면 생략).

## 4. 회사·서비스 이름

- **누구나 일상적으로 쓰는 플랫폼 이름은 그대로 쓴다.** 구글, 메타, 네이버, 카카오, AWS, 깃허브처럼 방송·기사에서도 광고 없이 흔히 말하는 이름이다. 가상의 이름으로 돌려 말하면 오히려 이해가 늦어진다. (2026-11-10 사용자 결정)
- 가능하면 **"구글·네이버 같은 플랫폼"처럼 한두 개를 함께** 든다. 특정 회사 하나를 밀어 주는 느낌을 줄인다.
- 하지 않을 것
  - 특정 회사를 깎아내리거나 사실이 아닌 내용 쓰기
  - 로고 이미지 넣기
  - 특정 제품을 사라고 권하는 문장 (이건 광고다)
- 광고주와 계약한 예문만 `[후원]` 표시를 붙인다. 표시 없는 회사 이름은 **설명을 위한 언급**이다.

## 5. 단계 (`stage`) 정하는 기준

**"이 용어를 가장 처음, 가장 자주 듣는 때는 프로젝트의 어느 단계인가?"**

| `stage` | 단계 | 이런 질문에 답하는 용어 |
|---|---|---|
| `discovery` | ① 발견·기획 | 무엇을, 누구를 위해, 어디까지 만드나? (요구사항, MVP, PoC) |
| `design` | ② 설계 | 어떤 구조로, 어떤 데이터로? (스키마, ADR, 디자인 토큰) |
| `build` | ③ 개발 | 어떻게 만들고 연결하나? (웹훅, 폴링, Git) |
| `test` | ④ 테스트·품질 | 맞게 만들었나? (유효성 검사, 단위 테스트, 평가 데이터셋) |
| `deploy` | ⑤ 배포 | 어떻게 내보내나? (CI/CD, 환경 변수, 롤백) |
| `operate` | ⑥ 운영 | 잘 돌아가고 있나? (로그, 모니터링, 장애, SLA) |
| `secure` | ⑦ 보안·개인정보 | 무엇을 지키고 막나? (OAuth, 위협 모델링, 비밀 관리) |
| `grow` | ⑧ 개선·확장 | 어떻게 키우나? (멀티테넌시, 국제화, A/B 테스트, 피벗) |
| `automate` | ⑨ 자동화·지속 개선 | 어떻게 스스로 좋아지게 하나? (피드백 루프, LLMOps, 에이전트) |

- 다른 단계에서도 자주 나오면 `also_stages`에 넣는다. 보안 용어는 대부분 여기에 `design`, `build`, `deploy`가 붙는다.

## 6. 등급 (`level`) 정하는 기준

| `level` | 이름 | 판단 질문 | 예 |
|---|---|---|---|
| 1 | 입문 | 개발자가 아닌 친구도 들어 본 적 있나? | API, 서버, 앱, 클라우드 |
| 2 | 기본 | 개발 공부 첫 달 안에 배우나? | Git, JSON, 스키마, 디자인 토큰 |
| 3 | 실무 | 현업 회의에서 설명 없이 그냥 쓰나? | 웹훅, CI/CD, OAuth |
| 4 | 심화 | 설계 면접에서 꼬리 질문으로 나오나? | 멀티테넌시, 경쟁 상태, 심층 방어 |

- 애매하면 **낮은 쪽**으로 정한다. 너무 쉬운 카드는 "이미 알아요"로 건너뛰면 되지만, 너무 어려운 카드는 이탈로 이어진다.
- 나중에 수강생 의견과 내 오답 기록으로 고친다.
