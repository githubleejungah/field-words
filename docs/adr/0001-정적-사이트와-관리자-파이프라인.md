# ADR-0001: 정적 사이트 + 관리자 파이프라인 구조

- 상태(Status): **채택(Accepted)**
- 날짜: 2026-11-09
- 결정한 사람: 프로젝트 오너(사용자). Claude가 선택지를 정리하고 추천함.

> ADR(Architecture Decision Record): 왜 그렇게 결정했는지 남기는 문서.
> 형식: 배경(Context) → 선택지(Options) → 결정(Decision) → 결과(Consequences)

---

## 1. 배경 (Context)

- 처음 계획: 나 혼자 쓰는 앱, 내 컴퓨터에서 실행(Streamlit + SQLite).
- 바뀐 요구:
  1. FDE 강의를 함께 듣는 **수강생에게 공개**한다.
  2. 마감은 강의 중간(**11/20 전후**).
  3. 용어 추출과 예문 생성에 **LLM**을 쓴다.
  4. 이 프로젝트로 **개발 공부**를 하고 포트폴리오로 쓴다.
- 제약:
  - Azure 무료 크레딧은 2026-12-02 만료, 강의는 12/04까지.
  - 수강생 수만큼 LLM 비용이 늘면 안 된다.
  - LLM API 키(Key: 유료 서비스를 쓰는 비밀 열쇠)가 공개되면 안 된다.

## 2. 선택지 (Options)

| | A. Streamlit 서버 앱 | B. 정적 사이트 + 관리자 파이프라인 ✅ | C. 유튜브 영상 |
|---|---|---|---|
| 구조 | 서버가 화면과 데이터를 모두 처리 | 공부 화면은 파일만으로 동작, LLM 작업은 내 컴퓨터에서 | 영상으로 배포 |
| 호스팅 비용 | 서버 필요 | 0원(GitHub Pages 등) | 0원 |
| LLM 비용 | 수강생 사용량만큼 증가 가능 | 내가 승인할 때만 발생 | 대본 작성 시 발생 |
| API 키 위험 | 서버에 보관, 관리 필요 | **공개 쪽에 키가 없음** | 없음 |
| 데이터 유지 | 무료 호스팅에서 SQLite가 재시작 때 사라질 수 있음 | JSON 파일로 Git에 저장 | 영상은 수정 불가 |
| 학습 기능(퀴즈·복습) | 가능 | 가능 | 불가 |
| 11/20 마감 | 가능 | 가능 | 제작 시간 때문에 어려움 |
| **개발 공부 가치** | 웹 기본기를 숨겨 줌 | **웹 기본기를 직접 다룸** | 개발보다 제작 |

## 3. 결정 (Decision)

**B. 정적 사이트 + 관리자 파이프라인**을 채택한다. 유튜브(C)는 Phase 3로 미룬다.

```
[내 컴퓨터: 관리자 파이프라인]              [인터넷: 수강생용 정적 사이트]
메모·대화 기록·기술 뉴스
 → LLM 용어 추출·예문 생성
 → 내가 검토·승인 (Human-in-the-loop)
 → glossary.json  ───(Git push → 자동 배포)──→  HTML + CSS + JavaScript
                                                 복습 기록은 각자 브라우저(localStorage)
```

## 4. "개발 공부에 더 도움이 된다"의 구체적인 이유

Streamlit은 Python만으로 웹 화면을 만들어 준다. 빠르지만 **웹이 어떻게 동작하는지를 대신 감춰 준다.**
정적 사이트는 그 부분을 직접 만들어야 한다. 그래서 FDE 실무에 필요한 기본기를 하나씩 손으로 익힌다.

| 직접 다루게 되는 것 | 배우는 개념 | FDE 실무에서 쓰이는 곳 |
|---|---|---|
| HTML, CSS, JavaScript | **프런트엔드(Frontend: 사용자가 보는 화면 쪽)** 기본기 | 고객 현장에서 데모 화면 수정 |
| glossary.json 설계 | **데이터 모델링(Data Modeling)**, **스키마(Schema: 데이터 구조 규칙)** | 고객 데이터를 시스템 형식에 맞추는 일 |
| fetch로 JSON 불러오기 | **클라이언트-서버 구조**, HTTP 요청 | API 연동 |
| localStorage에 복습 기록 저장 | **상태 관리(State Management)**, 브라우저 저장소 | 오프라인 동작, 사용자 설정 저장 |
| 공개 사이트와 관리자 파이프라인 분리 | **관심사 분리(Separation of Concerns)** | 시스템 설계 면접 단골 주제 |
| API 키를 공개 쪽에 두지 않기 | **비밀 관리(Secret Management)**, 보안 경계 | 고객사 보안 요구 대응 |
| GitHub에 올리면 자동 배포 | **CI/CD(Continuous Integration / Continuous Deployment: 코드를 올리면 자동으로 검사·배포하는 흐름)**, GitHub Actions | 현장 배포 자동화 |
| Python으로 LLM 파이프라인 | **ETL(Extract·Transform·Load: 뽑고, 바꾸고, 싣는 데이터 처리 흐름)**, 프롬프트 설계 | 고객 문서로 AI 기능 만들기 |

면접에서는 이렇게 말할 수 있다.
> "공개 영역과 LLM 영역을 분리해 API 키 노출과 사용량 비용 문제를 구조적으로 막았습니다. LLM 결과는 사람이 승인한 뒤에만 배포되도록 승인 게이트를 두었습니다."

## 5. 결과 (Consequences)

### 좋아지는 점
- 호스팅 비용 0원, 수강생이 늘어도 비용이 그대로다.
- 강의가 끝나는 12/04 이후에도 사이트가 유지된다.
- API 키가 공개 영역에 없다.
- 로그인이 없으므로 개인정보를 받지 않는다.

### 감수하는 점 (Trade-off: 얻는 것과 잃는 것의 맞바꿈)
- **수강생의 답변을 LLM이 실시간으로 채점할 수 없다.** 공개 사이트에 LLM이 없기 때문이다.
  → MVP는 **스스로 채점(Self-assessment)**: 모범 설명과 내 설명을 비교하고 "알았다/몰랐다"를 누른다.
  → 실시간 LLM 피드백이 꼭 필요해지면, 키를 숨긴 작은 중계 서버(**서버리스 함수, Serverless Function**)를 나중에 추가한다. 이때는 새 ADR을 쓴다.
- 복습 기록이 기기마다 따로 저장된다. 휴대폰과 노트북의 기록이 합쳐지지 않는다.
- 새 용어는 내가 파이프라인을 돌리고 배포해야 반영된다(실시간 아님).

## 6. 다시 검토할 조건
- 수강생이 "기기 간 기록 동기화"를 강하게 원할 때
- LLM 실시간 피드백이 핵심 기능이 될 때
- Phase 3에서 유튜브 자동 업로드를 만들 때
