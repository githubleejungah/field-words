# ADR-0004: 운영 자동화는 "자동 점검·제안 → 사람 승인 → 반영"으로 한다

- 상태(Status): **채택(Accepted)**
- 날짜: 2026-11-10
- 결정한 사람: 프로젝트 오너(사용자)가 "버그·보안·내용 업그레이드 자동화"를 요청. Claude가 구조를 제안.

## 1. 배경 (Context)
- 출시 후에도 버그를 잡고, 보안을 점검하고, 용어를 늘리고 다듬어야 한다.
- 사람이 매번 기억해서 하기 어렵다. 주간 사용량 한도가 남으면 그것도 쓰고 싶다.
- 동시에 원칙이 있다: **LLM 결과는 사람이 승인한 뒤에만 공개한다**(MVP 원칙, ADR-0001).

## 2. 선택지 (Options)
| | A. 완전 자동 (고치고 배포까지) | B. 자동 점검·제안 + 사람 승인 ✅ | C. 사람이 직접 점검 |
|---|---|---|---|
| 사람 시간 | 거의 없음 | 주 1회 약 30분 | 매번 많음 |
| 틀린 내용·버그가 공개될 위험 | 높음 | 낮음 | 낮음 |
| 빠뜨림 | 적음 | 적음 | 많음 |

## 3. 결정 (Decision)
**B를 채택한다.**
- 매주 예약 작업(`field-words-weekly`)이 `pipeline/check_all.py`를 돌리고, 수정 제안서·새 용어 후보·보강 제안·주간 보고서를 `pipeline/reports/`와 `pipeline/candidates/`에 만든다.
- 예약 작업은 `site/`를 고치지 않고, 커밋·푸시·배포·삭제를 하지 않는다.
- 사람은 보고서를 보고 승인한 것만 반영한다. 후보 용어는 `pipeline/promote.py`로 넣는다(검사 실패 시 자동으로 되돌림).
- 새 용어는 한 번에 20개로 고정한다. 남은 주간 한도를 정확히 읽을 수 없기 때문이다.

## 4. 결과 (Consequences)
### 좋아지는 점
- 점검을 잊지 않는다. 이번 구축 중에도 첫 실행에서 예문 속 전화번호 모양 숫자를 잡았다.
- 사람은 "판단"만 한다. 찾기·쓰기·검사는 자동이다.

### 감수하는 점
- Claude 앱이 켜져 있어야 실행된다.
- 수강생 의견(메일)은 아직 자동으로 읽지 못한다.
- 승인을 미루면 후보가 쌓이지 않도록 새 후보를 만들지 않는다 → 승인이 늦으면 용어도 늦게 는다.

## 5. 다시 검토할 조건
- GitHub에 올린 뒤: 점검을 GitHub Actions로 옮기고 Dependabot을 켠다.
- 의견 창구를 구글 폼으로 바꿀 때: 의견 분류·제안을 주간 작업에 넣는다.
