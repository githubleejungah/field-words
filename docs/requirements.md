## 1. 원문 (사용자 문장, 고치지 않음)

> * 엑셀 데이터 정리 → 간단한 데이터 질의(SQL 기초)
> * AI가 만든 코드에서 어디를 고치면 무엇이 바뀌는지 읽는 법
> * AI가 잘 틀리는 곳(숫자, 최신 정보, 출처)을 알아 두기 이걸 필드워드 게임에 넣는 방안을 제안해주세요.

> 실제 필드워드 사용자는 개발자들일거라 가정하고 아래 내용이 보여지는 건 아닌거죠?

> 좋습니다. 승인합니다.

(2026-11-24. 세 가지 중 이 문서는 세 번째 "AI가 잘 틀리는 곳"을 다룬다. 두 번째는 코드 가려 보기 게임, 첫 번째는 나중 단계로 나눴다 — 1-2.)

### 1-1. 승인한 방향 (Claude 제안, 사용자 승인 2026-11-24)

- 이름: **AI 답 검수**. AI가 쓴 짧은 답 몇 문장 중 틀린 곳을 고른다.
- 순서: 확신도 먼저 → 고르기 → 정답과 "이렇게 확인해요" 한 줄. 필드워드의 "판단 1번 + 확인 1번"과 착각 기록을 그대로 쓴다.
- 문제 유형 4가지: 숫자 · 최신 정보 · 출처/사실 · 코드.
- 상황은 **개발 현장**(사용자 = FDE 과정 수강생 · 개발자). 예: 호출 한도 계산, 지원 종료된 버전, HTTP 상태 코드, 없는 함수 · 옵션.
- 기존 용어 카드(호출 한도 · 캐시 · 폴링 · 웹훅 등)와 연결해 "이 용어에서 AI가 자주 틀리는 것"으로 보여 준다.
- 문제는 AI가 후보를 만들고 **사람이 승인한 것만** 공개한다. 정답도 공식 문서로 확인한 뒤 승인한다.

예시(형식 확인용):
> "호출 한도를 어떻게 잡아야 하나요?"에 대한 AI의 답
> ① 하루 1,200,000건이면 초당 약 140건이에요. ② 한도를 넘으면 서버는 보통 429 상태 코드를 돌려줘요. ③ 응답 헤더 `Retry-After`로 다시 보낼 시점을 알려 줄 수 있어요.
> 정답 ① (1,200,000 ÷ 86,400초 ≈ 14건) · 확인 방법: 하루 = 86,400초로 직접 나눠 보기

유형별 개발자 예시(첫 묶음 20개를 만들 때 방향 기준. 2026-11-24 대화에서 사용자가 "개발자 상황으로"를 승인). 문제로 넣기 전에 '바른 내용'도 공식 문서로 다시 확인한다(Q5).

| 유형 | AI의 틀린 문장 (예) | 바른 내용 | 확인 방법 |
|---|---|---|---|
| 숫자 | "하루 1,200,000건이면 초당 약 140건" | 약 14건 | 단위를 맞춰 직접 계산 |
| 최신 정보 | "Python 2는 아직 공식 지원돼요" | 2020-01-01 지원 종료 | 공식 문서의 지원 종료일 확인 |
| 출처/사실 | "429 상태 코드는 서버 내부 오류예요" | 429는 요청이 너무 많음(서버 내부 오류는 500) | 공식 명세(MDN 등)에서 코드 찾기 |
| 코드 | "자바스크립트 배열은 `contains()`로 들어 있는지 확인해요" | `includes()` | 실행하거나 공식 문서 검색 |
| 코드 | "`git push --force-safe`로 안전하게 덮어써요" | 없는 옵션. 실제는 `--force-with-lease` | `git push --help` 확인 |

- 사용자는 개발자(FDE 과정 수강생)로 본다. 영업 · 화장품 같은 다른 업종 상황은 쓰지 않는다(2026-11-24 사용자 확인).
- 문제마다 관련 필드워드 용어(호출 한도 · 캐시 · 폴링 · 웹훅 · 환각 · 평가 지표 등)를 잇는다(AS-4).

### 1-2. 나머지 두 가지 (이 문서 범위 밖 — 계정이 바뀌어도 이어지도록 계획을 여기 적어 둔다)

**(가) AI가 써 준 코드 읽기 → 코드 가려 보기 게임(`../field-words-3d-lab`)**

- 방법: 게임에서 이미 정한 남은 새 문제의 "노리는 착각"이 AI가 자주 만드는 실수와 거의 같다. 새 문제를 따로 만들지 않고, 아래 문제에 **"AI에게 한 요청 한 문장"**만 붙여 "AI가 써 준 코드" 틀로 보여 준다.

| 문제 (`id`) | AI에게 한 요청 (예) | 노리는 착각 = AI의 흔한 실수 |
|---|---|---|
| 기본값 (`default-basic`) | "설정값이 없으면 기본값을 넣어 줘" | `0`을 값이 없는 것으로 봄(`\|\|` vs `??`) |
| 로그 세기 (`while-basic`) | "로그를 다섯 번 남겨 줘" | 끝 조건이 하나 차이 |
| 같은지 비교 (`equal-basic`) | "입력한 번호가 맞는지 확인해 줘" | 글자 `"1"`과 숫자 `1`을 같다고 봄 |
| 가리기 (`mask-basic`) | "이름을 가려서 보여 줘" | `map`이 원래 목록까지 바꾼다고 봄 |
| 함께 기다리기 (`all-basic`) | "세 군데 결과를 한꺼번에 받아 줘" | 끝난 순서대로 담긴다고 봄 |
| 오류 잡기 (`trycatch-basic`) | "실패하면 오류를 잡아 줘" | `await` 없이도 잡힌다고 봄 |

- 바꿀 것(최소): 문제 데이터에 선택 칸 2개(요청 문장 · AI 작성 표시), 화면에 "AI에게 이렇게 부탁했어요" 한 줄. ①②③ 단계 · 복습 규칙 · 숫자는 그대로 둔다(4주 비교 조건 유지).
- 순서: 게임 쪽 24문제 확장 작업이 지금 묶음을 끝낸 뒤 → 게임 저장소 요구 문서에 질문 1개로 넣고 승인 → 남은 묶음에 반영. **4주 검증을 시작하기 전에** 넣어야 1주차 · 4주차 조건이 같다.
- 주의: 2026-11-24 기준 게임 저장소에는 다른 작업의 커밋 안 된 수정이 많다. 그 작업이 끝나기 전에는 게임 저장소 파일을 고치지 않는다.

**(나) 엑셀 → SQL 기초 (나중 단계)**

1. 필드워드 용어 카드 6개: SELECT · WHERE · ORDER BY · GROUP BY · JOIN · NULL. 비유는 "엑셀에선 필터 · 정렬 · 피벗 · VLOOKUP · 빈칸". 기존 카드 Text-to-SQL · NoSQL과 잇는다. 새 용어 후보 → 사람 승인 흐름(`pipeline/promote.py`)을 쓴다.
2. 게임 "SQL 쌍둥이" 문제: 실행은 자바스크립트 배열(`filter` · `sort` · `reduce`)로 하고, ① 해석 단계에 "SQL로 쓰면 `SELECT … WHERE …`"를 함께 보여 준다. 새 실행 엔진 없이 시작한다.
3. 진짜 SQL 실행(SQL 실행 라이브러리 사용)은 필드워드의 "외부 라이브러리 없음" 원칙과 부딪혀서, 4주 검증이 끝난 뒤 새 ADR로 정한다.

## 2. 인터뷰 (Q/A)

진행: 질문 1개씩 → 사용자 답. "추천 수용"은 Claude 추천을 받아들인 것.

Q1: 어디에 넣나? (화면 위치)
A1: 오늘의 학습에 섞고, 관련 용어 카드에 "AI가 자주 틀리는 것" 링크를 단다. 따로 메뉴는 두지 않는다. 이유: 따로 찾아가는 메뉴는 잘 안 쓰고, 매일 흐름에 섞어야 꾸준히 풀며 지루함도 준다. 기존 착각 기록을 그대로 쓴다. (추천 수용, 2026-11-24)

Q2: 하루 몇 문제? (양)
A2: 하루 새 문제 1개. 틀리거나 착각한 문제는 기존 복습 상자 규칙으로 다시 나온다. 이유: 하루 목표 10장(기존 `review.js` 규칙)을 밀어내지 않으면서 매일 새로움을 준다. (추천 수용, 2026-11-24)

Q3: 첫 묶음은 몇 개? (데이터 양)
A3: 20개, 유형마다 5개(숫자 · 최신 정보 · 출처/사실 · 코드). 이유: 하루 1개면 약 20일치, 네 유형을 고르게 다루고, 한 번 승인하기에 부담 없는 양. 강의는 12-04에 끝나지만 앱은 그 뒤에도 쓴다. 다음 묶음은 반응을 보고 더한다. (추천 수용, 2026-11-24)

Q4: 한 문제의 모양은? (입출력 예시)
A4: AI 답 문장 3개, 그중 틀린 문장은 항상 정확히 1개. 이유: 첫 묶음은 형식을 익히는 단계라 채점이 분명해야 착각 기록이 흐려지지 않는다. "틀린 곳 없음" 보기는 다음 묶음에서 다시 정한다. (추천 수용, 2026-11-24)

Q5: 정답 근거와 사람 개입은? (데이터 출처 · 사람 개입)
A5: ① 문제마다 공식 출처 링크(공식 문서 · 명세 · MDN 등) 1개 이상과 확인한 날짜 필수 ② 숫자 유형은 계산식 필수 ③ 출처나 계산식이 없는 후보는 검사 도구가 승인 전에 막는다 ④ 최종 공개는 사람 승인. 이유: 틀린 곳 찾기 문제의 정답이 틀리면 기능이 거꾸로 간다. 기존 사람 승인 흐름에 출처 검사만 더한다. (추천 수용, 2026-11-24)

Q6: 최신 정보가 낡으면? (실패 동작)
A6: 문제마다 "다시 확인할 날"을 적는다(최신 정보 유형은 확인일 + 6개월, 나머지 유형은 + 1년 — AS-1). 그날이 지나면 매주 자동 점검 보고서에 올리고, 사람이 "다시 확인함" 또는 "내리기"를 고를 때까지 새 문제로 내지 않는다(복습은 유지). 이유: 자동 점검은 제안까지, 반영은 사람(ADR-0004) 흐름에 얹는다. (추천 수용, 2026-11-24)

Q7: 성공 지표는?
A7: **공개한 문제의 정답 오류 신고 0건**(신고는 기존 "의견 보내기"). 학습 효과(착각 비율 변화)는 지표로 삼지 않는다(사용자 선택, 2026-11-24. 추천은 착각 비율 감소 + 오류 0건이었다).

Q8: 이번에 빼는 것은? (범위 밖)
A8: ① 앱 안에서 AI가 실시간으로 문제 만들기 ② 사용자가 문제 올리기 ③ 점수 공유 · 순위 ④ 틀린 문장을 직접 고쳐 쓰기(주관식 채점) ⑤ 영어 화면. 넣는 것: 오늘의 학습 하루 1문제, 용어 카드 연결, 출처 검사, 다시 확인할 날 보고. (추천 수용, 2026-11-24)

필드워드에서 그대로 이어받는 칸(새로 묻지 않음): 사용자 · 권한(누구나, 로그인 없음) · 개인정보(모으지 않음, 기록은 브라우저에만) · 비용(0원) · 성능(서버 없는 정적 사이트) · 콘텐츠 저작권(출처 문장 복사 금지, 설명은 새로 씀 — MVP 범위 v3 "콘텐츠 출처와 규칙").

## 4. 수용 기준 (EARS)

작성 규칙
- 한 행 = 요구 1개 = 시험 1개 후보.
- 패턴: U 항상 · E When(하면) · S While(동안) · O Where(경우) · W If…then(만약).
- 분류: SFR 기능 · DAR 데이터 · PER 성능 · SECR 보안 · CONR 제약.
- 근거: `Qn` 인터뷰 답 · `1-1` 승인한 방향 · `O` 관찰(기존 코드 · 문서) · `I` 추론 · `AS-n` 가정.
- 주어: "the app"은 공개 사이트, "the pipeline"은 관리자 파이프라인(문제 후보 검사 · 주간 점검).
