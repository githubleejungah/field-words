### 용어 그림 (Should) — ADR-0002
- "언제 쓰는지"를 그림으로 보여 준다. 그릴지 말지는 Claude가 판단하고, 그림은 사람이 승인한다.
- 그림 종류 5가지: 문제→해결(기본), 순서 흐름, 구조, 비교(혼동 쌍), 화면 모형.
- 방법: Mermaid(1순위), 직접 SVG + Lucide/Tabler 아이콘(2순위), 예문 상황 3종에는 Open Peeps(CC0).
- 관리자 파이프라인에서 미리 SVG로 바꿔 둔다(빌드 시점 렌더링).
- 그림의 `alt` 문장은 듣기 모드에서 TTS가 읽어 준다.
- 혼동 쌍 색: A쪽 `#f2e9e4`, B쪽 `#a7c4b5` + 진한 테두리 + 아이콘. 색만으로 구분하지 않는다(접근성).

### 발음과 소리 설계 (2026-11-10)
- **발음 칸(`pronunciation`)은 모든 용어에 필수**: 화면 표시용 한글 발음, 읽는 방식(글자/단어/섞어서), TTS 힌트, 다른 발음, 팁.
- 읽는 언어를 나눈다: 용어는 영어 음성, 뜻·예문은 한국어 음성.
- 웹은 휴대폰 무음 스위치 상태를 알 수 없다 → 앱 안에 소리 전환을 항상 보이게 둔다.
- 시간 타이머("1시간 끄기") 대신 **상황 프리셋**: 👀 보기만 / 🚶 이동 중(전부 읽기) / 🗣️ 말하기 연습(용어만). 학습 중 바꾼 프리셋은 **이번 학습 동안만** 유지한다.
- 이동 중 읽는 순서: 용어 → 발음 → 멈춤 → 뜻 → 비유 → 예문 → 그림 설명(`alt`) → 다음 카드.
- 프리셋은 "출력·입력·읽기 범위·속도·순서·자동 넘김" 설정 묶음이다. v2의 "출력·입력 따로 고르기"를 그대로 쓰고 이름만 붙인다. 설정은 localStorage에 저장한다(glossary.json에 넣지 않음).
- 현업 참고: 듀오링고 "지금 들을 수 없어요", 사전 앱의 눌러서 듣기, 팟캐스트 앱의 슬립 타이머·오디오 포커스.
- 한계: 웹·PWA·TWA는 오디오 포커스가 기기마다 다르다. TWA도 속은 크롬이라 같다. Media Session API(잠금 화면·이어폰 버튼)는 쓸 수 있다.

### 외국인 사용자 대비 (2026-11-10 사용자 요청, 나중 단계)
- 목표: 나중에 외국인도 쓸 수 있게 한다. 지금은 **나중에 고생하지 않을 준비만** 한다.
- v0.1부터 할 일(비용 거의 0): 화면 문구(버튼, 안내문)를 코드에 직접 쓰지 않고 `site/i18n/ko.json`에 모아 둔다. 이것이 **국제화(i18n: Internationalization, 여러 언어를 받을 수 있게 구조를 만드는 일)**다.
- 나중에 할 일: 언어별 파일 추가(`en.json`), 용어 데이터 번역. 이것이 **현지화(L10n: Localization, 실제로 그 언어와 문화에 맞게 옮기는 일)**다.
- 용어 데이터는 언어별 파일로 나누는 방식을 우선 검토한다(`glossary.ko.json`, `glossary.en.json`). 같은 `id`를 쓰므로 복습 기록은 언어를 바꿔도 이어진다. 결정은 실제로 시작할 때 ADR로 남긴다.
- 고려할 사용자 두 종류: ① 한국어 설명이 필요 없는 외국인 개발자(영어판) ② 한국 회사에서 일하는 외국인(한국 현업 표현 "배포", "기획", "QA 돌리다" 등을 배우려는 사람).
- 공개 체크리스트의 데이터 한계 안내문도 영어판이 필요하다.

### 퀴즈 사다리 (2026-11-10 사용자 제안)
쉬운 문제에서 어려운 문제로 올라간다. 알아보기(Recognition)가 떠올리기(Recall)보다 쉽고, 떠올리기가 말로 설명하기(Production)보다 쉽다.

| 칸 | 문제 | 입력 | 채점 | 라이트너 상자 |
|---|---|---|---|---|
| 1 | 용어 → 뜻 고르기 (객관식 4지) | 한 번 누르기 | 자동 | 1 |
| 2 | 뜻 → 용어 고르기 (객관식 4지) | 한 번 누르기 | 자동 | 2 |
| 3 | 예문 빈칸에 들어갈 용어 | 고르기 또는 입력 | 자동 | 3 |
| 4 | 면접 질문에 30초 동안 말로 답하기 → 모범 답변 | 말하기 → 한 번 누르기 | 스스로 | 4~5 |

- 복습 상자가 올라갈수록 문제가 어려워진다. 같은 용어를 여러 방식으로 만나서 기억이 단단해진다.
- 1~3칸은 **자동 채점**이라 "착각"(확실하다고 했는데 틀림)을 객관적으로 잡는다. 확신도 버튼과 함께 쓴다.
- 오답 보기(Distractor: 그럴듯한 틀린 보기)는 혼동 쌍 → 같은 단계·등급 용어 순서로 고른다. 데이터를 따로 쓰지 않는다.
- 4칸 흐름: 질문 → 30초 타이머 → 소리 내어(또는 속으로) 답하기 → 모범 답변(`interview_a`) 보기·듣기 → 맞음 / 일부 / 모름 중 한 번 누르기.

### 학습 효율 설계 — 뇌 학습 연구 기반 (2026-11-10)

**근거가 되는 원리**: 인출 연습(Roediger & Karpicke 2006), 간격 효과(Cepeda 외 2006·2008), 섞어 풀기(Kornell & Bjork 2008), 과신 오류 교정(Butterfield & Metcalfe 2001), 연속 재학습(Rawson & Dunlosky 2011), 피크엔드 법칙(Kahneman 외 1993), 스키마 연결(Tse 외 2007), 이중 부호화(Paivio), 사전 시험 효과(Kornell 외 2009), 85% 규칙(Wilson 외 2019, 계산 모델). 효과가 낮은 방법: 다시 읽기, 밑줄, 몰아서 보기(Dunlosky 외 2013). 실험실 결과라 수강생 반응을 보며 조절한다.

**① 오늘의 마무리 (하루 단위, Must)**
- 하루 목표의 마지막 구간에 포함. 2~3분.
- 순서: 착각 → 틀림·헷갈림 → 오늘 용어 + 혼동 쌍 섞기 → 맞힌 것 2~3개 → (선택) 내 말로 한 문장 → 확실히 맞힐 카드로 끝내고 구체적 칭찬.
- 다시 읽기가 아니라 다시 떠올리기. 순서는 섞고, 현재 퀴즈 칸보다 한 칸 쉽게 낸다.
- 중간 이탈자를 위해 쉼표 카드(5~7장마다)에 미니 마무리(방금 본 2장 다시)를 넣는다. 광고 자리와 같은 화면이다.
- 같은 학습 안에서 틀린 카드는 3장 뒤 → 10장 뒤에 다시 나온다(확장 간격).

**② 장기 기억 (주·달 단위, Must)**
- 라이트너 상자를 5개(최대 14일)에서 **7개(1·2·4·7·15·30·60일) + 장기 기억 유지(120일마다)**로 늘린다. 면접은 몇 달 뒤일 수 있다.
- 상자 4 이상에서 틀리면 두 칸만 내린다(오래 기억한 것을 처음부터 하지 않게).
- 복습 먼저, 새 카드는 하루 목표의 남는 자리만큼(복습 빚 방지).
- 혼동 쌍 구별 문제는 두 용어를 각각 한 번씩 본 뒤에(간섭 방지).
- **장기 기억 = 30일 이상 간격을 두고 다시 맞힌 용어.** 대시보드와 성장 그래프의 핵심 숫자로 쓴다.
- Should: "실전에서 들었어요"·"설명해 줬어요" 버튼, 잠들기 전 듣기, 다음 날 첫 문제는 어제 틀린 카드, FSRS(Phase 2).

**③ 틀렸을 때 (Must)**
- 원칙: 틀리는 것은 학습에 도움이 되지만, 부정적인 감정은 방해가 된다. **놀람과 호기심은 살리고, 창피함과 위협감은 없앤다**(부담 낮은 시험).
- 빨간 ✗·버저·진동 대신 **내 답과 정답을 나란히** 보여 준다(혼동 쌍 색). 차이 한 줄 + `pitfall`.
- 착각(확실 → 틀림)일 때만 "💡 의외죠?"로 놀람을 살린다.
- 하루 목표는 **푼 카드 수**로 채운다. 감점 없음, 순위표 없음.
- Should: 연속 3번 틀리면 한 칸 쉽게(대부분 맞히고 가끔 틀리는 난이도 유지), "오늘 바로잡은 것 n개".
- 말투 규칙은 `docs/콘텐츠_작성_가이드.md` 8장.

### 면접 연습 (2026-11-10, Should 1순위)
- 별도 버전을 만들지 않고 **앱 안의 모드**로 넣는다. 데이터(`interview_q`, `interview_a`, 면접 예문, `pitfall`)와 화면(카드, TTS, 확신도 버튼)을 그대로 쓴다.
- 흐름: 질문 무작위 출제 → 30초 타이머 → 소리 내어 답하기 → 모범 답변 → 스스로 채점.
- 원래 성공 지표("무작위 10개 중 8개를 30초 안에 설명")와 같은 형식이다. 이 모드의 기록이 곧 성공 지표 측정이 된다.
- 나중 단계(Phase 2): 용어에 묶이지 않는 FDE 면접 질문 은행. 고객 상황 대처, 시스템 설계, 장애 대응, 경험 질문(STAR: 상황·과제·행동·결과 순서로 답하는 법).
- LLM 실시간 채점은 ADR-0001 조건에 따라 나중에 검토한다.

### 화면이 스스로 설명하기 (Should)
- 대시보드 각 영역에 ⓘ 버튼 → 그 영역을 만든 개발 용어 카드. 예: 진행 링 → 도넛 차트, 성장 그래프 → 시계열.
- "개발자 보기" 켜기 → 화면 뒤의 JSON 데이터와 localStorage 값을 보여 준다.
- 누르지 않으면 아무 일도 없다(1-tap 원칙 유지).

### 광고 원칙 (출시 후. 지금은 자리만 설계)
- 위치: **쉼표 카드(5~7장마다)**, 대시보드, 검색 결과 3번째, 완료 화면. 중간 이탈자도 광고를 보게 하되 카드 사이에만 둔다.
- 금지: 카드·퀴즈를 푸는 도중, 음성 흐름 중간, 큰 버튼 바로 옆, 오디오 광고.
- 걷기(듣기) 모드: 소리 없는 화면 광고만.
- 광고를 학습 재료로: 광고 옆 "이 칸 뜯어보기" → 네이티브 광고, CPM, 비개인화 광고 같은 광고 기술 용어 카드.
- 광고 빈자리(No-fill)는 학습 카드로 채운다(백필). 이것은 **덤**이다. 혼동 쌍은 원래 학습 계획에 들어 있어 광고와 관계없이 학습한다.
- 후원 예문: 직접 계약한 광고주 제품을 예문 1개에 넣고 `[후원]` 표시. 뜻(definition)은 광고주가 바꿀 수 없다. 사용자가 늘어난 뒤 검토.
- 쓰지 않음: 보상형 광고(자주 안 쓰는 사람에게 광고가 몰리고 학습 동기를 해친다).
- 확인 필요(출시 시점): TWA 앱의 AdSense 사용 조건, 광고 제거 결제 시 Play Billing 의무, 개인정보 처리방침·동의 화면. → ADR-0001("개인정보를 받지 않는다")과 부딪히므로 새 ADR을 쓴다.

## 0. 범위 변경 v2 (2026-11-09) — 아래 본문보다 우선한다

### 바뀐 점
1. **사용자 확대**: 나 혼자 → **FDE 강의를 함께 듣는 수강생**
2. **마감 앞당김**: 12/4 → **강의 중간(4회차 11/21 전후)**
3. **신규 용어 자동 조사 + 영상 추가 자동화** 요구 추가

### 구조 결정안: "관리자 파이프라인 + 공개용 정적 사이트"

```
[내 컴퓨터: 관리자 파이프라인]                [인터넷: 수강생용 사이트]
강의 메모 / 대화 기록 / 기술 뉴스
   → LLM 용어 추출·예문 생성
   → 내가 검토·승인 (Human-in-the-loop)
   → glossary.json 생성 ─────────────────→ 정적 웹사이트(검색·카드·복습)
                                              복습 기록은 각자 브라우저에 저장
```

- **정적 사이트(Static Site: 서버 없이 파일만으로 동작하는 웹사이트)**로 배포한다.
  - 수강생은 로그인 없이 링크로 접속한다 → 개인정보를 받지 않는다.
  - 복습 기록은 각자 브라우저(localStorage)에 저장된다.
  - LLM 호출은 내 컴퓨터에서만 한다 → **API 키가 노출되지 않고**, 수강생 사용량만큼 비용이 늘지 않는다.
  - 무료 호스팅(GitHub Pages 등) 사용 → Azure 크레딧 만료(12/2)와 상관없이 강의 끝(12/4)까지 유지된다.

### 단계(Phase)

| 단계 | 기한 | 내용 |
|---|---|---|
| **Phase 1** | ~11/20 | 공개 사이트: 검색, 용어 카드(상황별 예문 2~3개), 오늘의 복습. 관리자: 붙여넣기 → 추출 → 승인 → JSON |
| **Phase 2** | ~12/4 | 신규 용어 **반자동** 조사: 기술 뉴스·공식 블로그에서 후보 수집 → 내가 승인. 수강생 용어 요청 받기 |
| **Phase 3** | 강의 후 | 승인된 용어로 **설명 영상 반자동 생성**: 대본(LLM) → 음성(TTS) → 화면 구성 → 영상 합성 → 내가 검수 후 업로드 |

### 상황별 학습 모드 (2026-11-09 추가, Must)

걷기, 대중교통, 공공장소처럼 상황이 계속 바뀐다. 그래서 **입력과 출력을 따로 고를 수 있게** 하고, 공부 중에도 한 번에 바꿀 수 있게 한다.

| 모드 | 출력(앱 → 나) | 입력(나 → 앱) | 어울리는 상황 |
|---|---|---|---|
| 👀 보기 | 화면 글자 | 큰 버튼(알았다/몰랐다) | 서서 기다릴 때 |
| 🎧 듣기 (핸즈프리) | **TTS로 읽어 줌**: 용어 → 잠시 멈춤 → 뜻 → 예문 | 없음 또는 이어폰 버튼 | **걸을 때** |
| ✍️ 쓰기 | 화면 글자 | 키보드로 설명 쓰기 → 모범 설명과 비교 | 앉아 있을 때 |
| 🗣️ 말하기 (선택) | 화면 또는 음성 | **STT로 말해서 설명** → 모범 설명과 비교 | 혼자 있을 때 |

- 출력(보기/듣기)과 입력(없음/쓰기/말하기)은 **각각 따로 켜고 끈다.** 예: 듣기 + 말하기, 보기 + 쓰기.
- 화면 위에 **모드 전환 버튼**을 항상 보이게 둔다. 진행 중인 카드와 복습 기록은 모드를 바꿔도 이어진다.
- 말하기는 **기본으로 꺼져 있다.** 공공장소에서 갑자기 마이크가 켜지지 않게 한다.
- 채점: MVP는 스스로 채점(Self-assessment). LLM 채점은 ADR-0001의 조건에 따라 나중에 검토한다.

기술 메모
- 듣기: 브라우저 내장 **Web Speech API의 speechSynthesis**. 무료, 서버 불필요.
- 말하기: 같은 API의 **SpeechRecognition**. 크롬·엣지 중심 지원, 브라우저마다 다름. 크롬에서는 음성이 Google 서버로 전송될 수 있음 → 처음 켤 때 안내한다.
- 위험: 휴대폰 화면이 꺼지면 브라우저가 읽기를 멈출 수 있다 → 실제 휴대폰으로 일찍 시험한다. 해결 후보: **Media Session API**, PWA(Progressive Web App: 앱처럼 설치되는 웹사이트).
- Could: 걷기 감지 자동 전환(휴대폰 움직임 센서 활용). MVP에서는 수동 전환.

### 학습 상태 진단 (2026-11-09 추가)

목표: "아는 것 / 모르는 것 / **헷갈리는 것**"을 구분하고, 특히 **아는 것처럼 보이는 착각**을 잡아낸다.
조건: 카드 하나당 입력은 **최대 한 번 누르기(1-tap)**. 쓰기·말하기는 선택이다.

**신호 3종 (입력 부담이 적은 순서)**

| 신호 | 사용자가 하는 일 | 잡아내는 것 |
|---|---|---|
| ① 암묵적 신호(Implicit Signal) | **아무것도 안 함** | 뜻을 보기까지 걸린 시간, 다시 본 횟수, "알았다" 뒤 다음 복습에서 "몰랐다"로 바뀐 횟수(망각) |
| ② 확신도 버튼 | 한 번 누르기: **확실 / 헷갈림 / 모름** | 스스로 느끼는 확신 |
| ③ 혼동 쌍 퀴즈 | 한 번 누르기: 비슷한 용어 중 고르기 (예: 웹훅 vs 폴링) | 실제로 맞는지, **무엇과 헷갈리는지** |

**학습 상태 5단계 = 확신도 × 정답 여부**

| | 정답 | 오답 |
|---|---|---|
| 확실하다고 함 | ✅ 앎 | 🚨 **착각(과신)** — 가장 위험, 최우선 복습 |
| 헷갈린다고 함 | 🟡 불안한 앎 | 🟠 헷갈림 (어떤 용어와 헷갈리는지 기록) |
| 모른다고 함 | — | ⚪ 모름 |

- 이 방식을 **확신도 기반 평가(Confidence-Based Assessment)**라고 한다.
- 혼동 쌍 데이터: glossary.json에 `confusable_with` 필드를 둔다.
  - **결정 주체: Claude(LLM)** (2026-11-09 사용자 결정. 사람의 주관이 섞이지 않게 하려는 목적)
  - 품질 장치 ①: 객관적 기준으로만 넣는다 — 같은 분야, 이름이나 역할이 비슷함, 실무에서 실제로 섞어 쓰는 사례가 있음, 차이를 한 문장으로 설명할 수 있음
  - 품질 장치 ②: 다른 프롬프트로 한 번 더 검사한다(**LLM-as-a-Judge**: LLM이 다른 LLM의 결과를 평가하는 방식). 통과한 쌍만 넣는다
  - 품질 장치 ③: 실제 퀴즈 오답 데이터로 보정한다. 자주 틀리는 조합은 새 쌍으로 추가하고, 아무도 헷갈리지 않는 쌍은 뺀다 → **데이터 기반 개선**

**대시보드(Dashboard: 한눈에 보는 현황판)**
- 상태별 용어 수 (앎 / 불안한 앎 / 헷갈림 / 착각 / 모름)
- 🚨 착각 목록, 🟠 자주 헷갈리는 쌍 Top 5
- 성장 그래프: 날짜별 "앎" 용어 수
- 오늘의 학습 계획: 착각 → 헷갈림 → 모름 → 복습 예정 순으로 자동 배치, 예상 시간 표시

**우선순위**
- Must: ② 확신도 버튼, ③ 혼동 쌍 퀴즈(기본 몇 쌍), 5단계 상태 분류, 상태별 개수와 착각·헷갈림 목록
- Should: 성장 그래프, 오늘의 학습 계획 자동 생성
- Could: ① 암묵적 신호 분석

**기술 메모**: 모든 계산은 브라우저 JavaScript에서 하고 데이터는 localStorage에 둔다. 그래프는 차트 라이브러리(예: Chart.js)를 쓴다. Streamlit 없이도 가능하므로 ADR-0001은 그대로 유지한다.

### 하루 목표와 응원 (2026-11-09 추가)

**① 첫 실행 설문 (온보딩, Onboarding: 처음 쓰는 사람을 안내하는 과정)** — 3문항, 모두 한 번 누르기
1. 하루에 공부할 수 있는 시간은? → 5분 / 10분 / 20분 / 30분 (카드 수로 바꿔 목표 설정)
2. 주로 언제 공부하나요? → 출근길 / 점심 / 퇴근길 / 자기 전
3. 주로 어디서 하나요? → 걸으면서 / 대중교통 / 앉아서 → **기본 학습 모드 자동 추천**
- 2번은 **실행 의도(Implementation Intention: "언제, 어디서 하겠다"를 미리 정하면 실천율이 높아지는 원리)**를 만든다.
- 목표는 언제든 바꿀 수 있다.

**② 진행 현황 보여 주기**
- **진행 링(Progress Ring)**: 오늘 목표 대비 채운 비율. 예: 12 / 20장
- 남은 양을 **시간으로** 보여 준다: "8장 남음 · 약 3분"
- 목표에 가까워질수록 동기가 커지는 **목표 경사 효과(Goal-Gradient Effect)**를 활용: 80%를 넘으면 "거의 다 왔어요" 표시

**③ 응원 장치**
- **최소 목표 + 목표** 두 단계: 바쁜 날은 최소 목표(예: 3장)만 채워도 오늘 성공으로 인정 → 포기 방지
- **연속 학습일(Streak)** + **쉬는 날 허용(Streak Freeze)**: 주 1회는 쉬어도 기록이 끊기지 않음 → 죄책감 대신 꾸준함
- **구체적인 칭찬**: "열심히 했어요" 대신 "착각하던 OAuth를 바로잡았어요", "헷갈리던 웹훅·폴링을 3번 연속 맞혔어요" (**과정 칭찬, Process Praise**)
- **이정표(Milestone)**: 앎 10개, 50개, 100개 달성 / 혼동 쌍 첫 정복
- 하지 않을 것: 목표를 못 채웠다고 혼내는 문구, 빨간 경고 → 앱을 싫어지게 만든다(**다크 패턴, Dark Pattern** 회피)

**우선순위**
- Must: 온보딩 설문, 진행 링, 남은 양 표시, 최소 목표
- Should: 연속 학습일과 쉬는 날 허용, 구체적인 칭찬
- Could: 이정표 배지, 정해진 시간 알림(푸시 알림은 PWA 설정이 필요)

### 앱 스토어 배포 검토 (2026-11-09, 나중 단계)

| 방법 | 비용 | 조건 | 시기 |
|---|---|---|---|
| **PWA 설치** ("홈 화면에 추가") | **무료** | 사이트를 PWA로 만들면 휴대폰에 앱처럼 설치됨. 스토어 심사 없음 | Phase 1 후반 |
| **구글 플레이 스토어** | **등록비 1회 약 25달러** (연회비 없음, 확인 필요) | PWA를 **TWA(Trusted Web Activity: 웹사이트를 안드로이드 앱으로 감싸는 방식)**로 포장. 도구: Bubblewrap, PWABuilder. 신규 개인 개발자 계정은 **비공개 테스트(최소 12명, 14일 이상)**를 먼저 거쳐야 함(확인 필요). 신원 확인 필요 | 강의 후 |
| 애플 앱 스토어 | 연회비 약 99달러 | 맥 컴퓨터와 별도 심사 필요 | 검토 안 함 |

- 같은 강의 수강생이 비공개 테스트의 **테스터**가 될 수 있다.
- 정책과 금액은 바뀔 수 있으므로 진행 시점에 공식 문서로 확인한다.

### 원칙
- **자동 게시 금지**: 용어·예문·영상은 모두 사람이 확인한 뒤 공개한다. LLM 환각이 수강생에게 그대로 퍼지는 것을 막는다.
- **강의 자료 보호**: 강의 슬라이드·문장을 그대로 싣지 않는다. 일반적으로 쓰이는 업계 용어와 내가 새로 쓴 설명·예문만 싣는다. (강사님 허락은 받지 않기로 결정, 2026-11-09)

### 결정 기록 (2026-11-09)
- **구조 확정**: 관리자 파이프라인(로컬) + 공개용 정적 사이트. 자세한 이유는 `docs/adr/0001-정적-사이트와-관리자-파이프라인.md` 참고.
- **유튜브는 Phase 3**으로 미룬다. 영상은 직접 제작하며, TTS·자막은 Google 무료 도구 활용 예정.
- Phase 3 시작 전 확인: YouTube Data API로 자동 업로드할 때의 공개 상태 제한과 할당량(Quota).
- **뉴스 저작권**: 기사 문장을 복사하지 않고, 용어와 출처 링크만 저장한다. 설명은 새로 쓴다.

## 1. 문제 정의 (Problem Statement)

- 강의와 면접에서 개발 용어를 몰라 설명을 따라가지 못한다.
- 용어를 들어도 따로 모아 두지 않아 다시 잊는다.
- 용어를 "아는 것"과 면접에서 "말로 설명하는 것"은 다르다.

## 2. 목표와 성공 지표 (Success Metrics)

| 지표 | 목표 (12/4까지) |
|---|---|
| 쌓인 용어 수 | 100개 이상 |
| 복습 지속 | 2주 연속, 하루 10개 이상 복습 |
| 설명 능력 | 무작위 용어 10개 중 8개를 30초 안에 말로 설명 |

## 3. 기능 범위 (MoSCoW: 우선순위 분류법)

### Must (꼭 있어야 함) — 1차 완성 기준
1. **용어 카드 저장·조회·수정·삭제 (CRUD)**
   - 카드마다 **상황별 예문 2~3개**: 업무 회의, 면접 답변, 문서·코드 리뷰 중에서 고른다
   - 이유: 단어 뜻만 아는 것으로는 "언제 쓰는지"를 알 수 없다 (2026-11-09 사용자 피드백)
2. **검색**: 영어·한국어 모두
3. **용어 자동 추출**: 강의 메모나 대화를 붙여 넣으면 LLM이 용어 후보를 뽑는다
   - 사람이 확인하고 골라서 저장한다 (**Human-in-the-loop**: 사람이 중간에서 검토하는 구조)
4. **오늘의 복습**: 간격 반복(Spaced Repetition). 알았다/몰랐다 버튼
5. **시드 데이터(Seed Data: 처음부터 넣어 두는 데이터)**: 지금까지 대화에서 나온 용어 약 40개

### Should (있으면 좋음) — 시간이 되면
6. **면접 모드**: 용어를 묻고 → 내가 설명을 쓰면 → LLM이 피드백
7. 태그별 보기 (보안, 데이터, 기획, AI, 인프라 등)
8. **Claude Code 대화 기록 가져오기 (Ingestion: 외부 데이터를 시스템으로 들여오는 일)**
   - 위치: `~/.claude/projects/<프로젝트>/*.jsonl` (2026-11-09 확인: 약 27개 세션 기록 존재)
   - 형식: JSONL (한 줄에 JSON 하나씩 들어 있는 로그 파일)
   - 흐름: 파일 읽기 → 사용자·Claude 대화 텍스트만 추출 → **개인정보 가리기(Masking)** → 기존 용어 추출 기능으로 보내기
   - 개인정보 가리기 대상: 전화번호, 이메일, 사람 이름, API 키
   - 모든 처리는 **내 컴퓨터 안에서만** 한다
   - 위험: 이 로그 형식은 공개된 공식 규격이 아니라서 바뀔 수 있다 → 읽는 부분을 따로 분리해 둔다 (어댑터 패턴)
9. **강의별 신규 용어 수 그래프**: 회차마다 새 용어가 몇 개 나왔는지 본다. 새 용어가 줄어들면 **포화(Saturation)**에 가까워진 것이다

### Could (여유가 있으면)
8. 음성으로 답하기 (STT)
9. 용어 읽어 주기 (TTS)
10. CSV 내보내기 (Anki 같은 다른 앱으로 옮기기)

### Won't (이번에는 안 함)
- 최신 용어 트렌드 자동 수집
- 영상 자동 생성
- 로그인, 여러 사용자
- 모바일 앱

## 4. 데이터 모델 (Data Model: 저장할 정보의 구조)

**Term (용어)**

| 필드 | 예시 |
|---|---|
| term_en | OAuth |
| term_ko | 오어스, 위임 인증 |
| definition | 비밀번호를 주지 않고, 플랫폼이 직접 "이 앱에 권한을 줄까요?"라고 묻는 표준 승인 방식 |
| analogy | 호텔 열쇠 대신 특정 층만 열리는 카드키를 받는 것 |
| examples | 상황별 예문 2~3개 (아래 Example 표) |
| tags | 보안, 인증 |
| related | 패스키, SSO |
| source | 대화 2026-11-09 / FDE 1회차 |
| created_at | 2026-11-09 |

**Example (예문)** — 용어 하나에 2~3개

| context (상황) | sentence (예문) |
|---|---|
| 업무 회의 | "네이버 연동은 OAuth로 붙이면 고객 비밀번호를 저희가 보관할 필요가 없습니다." |
| 면접 답변 | "계정 연동은 OAuth로 처리해서 앱이 비밀번호를 저장하지 않게 설계했습니다." |
| 문서·코드 리뷰 | "토큰 만료 시 OAuth 리프레시 흐름이 빠져 있어요. 재인증 처리를 추가해 주세요." |

**Review (복습 기록)**

| 필드 | 설명 |
|---|---|
| term_id | 어떤 용어인지 |
| box | 라이트너 상자 1~5 (높을수록 잘 앎) |
| next_review_at | 다음 복습 날짜 |
| history | 알았다/몰랐다 기록 |

**간격 반복 규칙 (라이트너 시스템, Leitner System)**
- 알았다 → 다음 상자로 이동. 몰랐다 → 1번 상자로.
- 상자별 복습 간격: 1일 → 2일 → 4일 → 7일 → 14일
